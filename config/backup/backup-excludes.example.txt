# backup-excludes.txt — what restic does not back up. An EXAMPLE; copy it.
#
#   cp config/backup/backup-excludes.example.txt config/backup/backup-excludes.txt
#   $EDITOR config/backup/backup-excludes.txt
#
# A fresh clone runs on this file directly: `engine/lib/roots.sh` resolves
# `PAZRAS_BACKUP_EXCLUDES` to the install's own list when it exists and falls
# back to this one when it does not, and the master config's `RESTIC_EXCLUDES`
# reads that variable. So `familiar backup run` has a working exclude list on
# the day you clone, and the copy is where YOUR machine's exceptions go —
# paths, disks and services that are yours and have no business in a template.
#
# WHY AN EXCLUDE LIST IS NOT OPTIONAL. `restic backup --exclude-file` fails
# outright (rc=1, nothing backed up) on a file it cannot read. There is no
# built-in default and no "exclude nothing" fallback.
#
# Usage, spelled out because the default is long:
#   restic backup <paths> --exclude-file <install>/config/backup/backup-excludes.txt
#
# Patterns are restic's: a bare `name` matches any path component named that,
# `/leading` is anchored to the backup root, `**` crosses separators. They are
# matched against paths INSIDE the snapshot, relative to what you passed on the
# command line — so keep them relative (no leading `/`) and they survive a move
# to a new machine, which is the whole point of a versioned config.

# ── secrets: must never enter a repository ─────────────────────────────────
# A restic repo is encrypted, and that is not a reason to put a key in it: the
# repo travels to disks and providers, gets copied to a new laptop, and outlives
# the key it holds. A key that was ever inside is a key to rotate.

# ── a backup destination must not live inside a backup source ──────────────

.cache/pazras-mirror/

# ── bulk data that is regenerable, and therefore not recovery ──────────────

# separately instead: versioning 27 GB of immutable input per run is storage
# spent on nothing, and the manifest is what makes it re-acquirable.
